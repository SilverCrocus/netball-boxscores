Architecture Approaches

How should we structure the NETPULSE platform?

A

Next.js Full-Stack Monolith (Recommended)

Frontend + API in one Next.js app

Pros

  • Single codebase, single deployment on Render
  • Next.js API routes handle data fetching, caching, and auth
  • Server Components for SSR with real-time hydration
  • WebSocket support via custom server for live scores
  • Simplest to build and maintain as a personal project

Cons

  • Scaling frontend and backend independently requires refactoring later
  • WebSocket needs a custom server (not pure serverless)

Stack: Next.js 15 + App Router + Server Actions + Prisma ORM + PostgreSQL + NextAuth.js + Socket.io

B

Separate Frontend + Backend API

Next.js frontend + Express/Fastify backend API

Pros

  • Clean API boundary — backend could serve mobile app later
  • Independent scaling and deployment
  • Backend handles all data scraping/caching centrally

Cons

  • Two repos/deployments to maintain (2x Render services)
  • More complex local dev setup
  • CORS, auth token management between services
  • Overkill for a personal project at this stage

Stack: Next.js 15 (frontend) + Fastify (API) + PostgreSQL + Passport.js + Socket.io

C

Next.js + Supabase BaaS

Next.js frontend with Supabase for database, auth, and real-time

Pros

  • Supabase Realtime handles live score subscriptions out of the box
  • Built-in auth (email, OAuth, magic link)
  • PostgreSQL with auto-generated REST and GraphQL APIs
  • Less backend code to write

Cons

  • Vendor lock-in to Supabase
  • Still need a background worker for data scraping (can't run in Supabase)
  • Free tier limits may be hit with real-time features
  • Adds Supabase as a dependency alongside Render

Stack: Next.js 15 + Supabase (DB + Auth + Realtime) + Render (for scraper/worker)
