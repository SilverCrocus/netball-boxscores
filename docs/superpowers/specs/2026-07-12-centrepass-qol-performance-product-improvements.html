Executive summary

Optimise the work before changing the language.

The audit found a strong sports product underneath an overly heavy first load and several unfinished journeys. The biggest wins come from bounded queries, caching, on-demand event data, responsive corrections, and exposing capabilities that already exist in the repository.

Decision: stay with TypeScript

The measured delay is predominantly database and server-rendering latency. Rust does not reduce the number of rows queried, events serialized, DOM nodes rendered, or database round trips. It remains a future option only behind a captured CPU profile and a material benchmark win.

Phase 1 · Entry experience

Homepage feed

The homepage becomes a current sports hub, not a rendered archive of the whole season.

Initial content order

  1. All live matches.
  2. Up to four upcoming fixtures.
  3. The latest completed stage or round.
  4. Additional recent results up to eight completed cards total.
  5. A deliberate View previous rounds action.

Filters and pagination

  • Season, team, stage/round, and Upcoming/Results controls.
  • URL search parameters preserve sharing and browser navigation.
  • Cursor pagination based on scheduledAt and id.
  • Maximum eight matches per history request.
  • Explicit loading, retry, empty, and polite live-region states.

Acceptance gate

  • The initial completed query is hard-bounded to eight.
  • The production DOM is below 2,000 nodes.
  • Postseason state identifies the Grand Final winner from data.
  • Every filter deep-links and restores correctly.

Phase 1 · Correctness

Season-scoped standings

Invariant. No standings query may execute without a selected competition ID.
  • Use a shared latest/selected competition helper across standings, teams, players, and home filters.
  • Derive the displayed year from the competition row; remove hardcoded `2026` presentation.
  • Team rank and record use the same selected/default competition.
  • Invalid season parameters fall back safely and canonicalize the URL.
  • Test multiple competitions containing the same teams.

Mobile ladder

Below the medium breakpoint, use readable ladder cards rather than requiring horizontal table discovery. Each card shows rank, team, games played, W–L–D, goal percentage, and points.

Acceptance gate

  • Header year, standings rows, and team-profile record always agree.
  • Essential mobile values require no horizontal scrolling.
  • Desktop table semantics and definitions remain intact.

Phase 1 · Empty-state product design

Live is always useful

The Live navigation remains readable and clickable even when no match is underway.

No live match
  • Show “No match is live right now.”
  • Show the next scheduled match and local countdown.
  • Show the latest result and followed-team context when available.
  • Offer reminder/sign-in and all-fixtures actions.
One live match

Redirect directly to its live match page, preserving the current fast path.

Several live matches

Render a live-match chooser rather than silently selecting the first database row.

Acceptance gate

  • /live never redirects home solely because no match is live.
  • No-live, one-live, and multiple-live states have tests.
  • Imminent copy says “Starts in” and never falsely claims live status.

Implementation rules

  • Prefer explicit server query wrappers and TTLs; never share-cache user data.
  • Remove forced dynamic rendering from teams and standings only after cache-safe wrappers exist.
  • Separate stable homepage history from live/upcoming state.
  • Use Suspense only with stable fallback geometry and measurable first-paint value.

Server timing

Record named durations for competition, live, upcoming, history, match base, score flow, events, player profile, and total render. Expose safe aggregate values through structured logs or Server-Timing.

Phase 2 · Payload design

Match detail on demand

Initial box-score payload

  • Match identity, status, score, teams, quarters, explicit player-stat fields, and summary values.
  • Only the score-flow fields required for Match Momentum.
  • No matchEvents before Play by Play is activated.

Timeline endpoint

GET /api/matches/{matchId}/events
  ?limit=75
  &cursor=...
  &quarter=4
  &type=turnover
  &team=...
  • Newest first, maximum 75, cursor-paginated.
  • Quarter, event type, and team filters.
  • Typed 400/404/retryable failure states.
  • Live socket entries respect the user's active filters.

Charts and mobile tables

  • Dynamically import Recharts-backed screens and reserve their height.
  • Provide a textual/table fallback.
  • Sticky Player column, edge fade, and “Swipe for more stats” hint on mobile.
  • Show compact Key Stats before the full matrix.

Acceptance gate

  • Network capture proves zero event transfer before tab activation.
  • All initial Prisma relations use explicit selects.
  • Event filters and pagination pass completed/live tests.
  • Chart loading causes no layout jump.

Phase 2 · Responsive and media quality

Profiles that hold together

Team profile

  • Remove forced line breaks after each word; use fluid, phrase-aware wrapping.
  • Maximum three lines at 320 px and two lines on desktop.
  • Recent Form gains scroll snapping, directional controls, edge cue, and View all results.

Player profile

  • Missing or unusable portrait always produces high-contrast initials.
  • Percentage changes state their comparison baseline.
  • Impact, NetPoints, Gains, CPR, FD, and super-shot notation use shared definitions.
  • Biography provenance is recorded and contradictory enrichment is flagged.

Canonical team assets

Store normalized local assets for the eight league teams under public/teams/{slug}. Keep upstream URLs for provenance/fallback, then use abbreviation tiles as the final safe fallback.

Acceptance gate

  • All team badges are legible on light and dark cards.
  • Missing portraits show initials in both themes.
  • Team headings work at 320, 390, 768, 1024, and 1440 px.

Phase 3 · Product completion

Account, personalization & search

Account discovery
  • Desktop sidebar bottom section shows Sign in or avatar, Settings, and Sign out.
  • Mobile gains a deliberate More/account destination rather than a crowded silent addition.
  • Settings becomes reachable without manually entering its URL.
Followed teams
  • Signed-in homepage shows My Teams after live/upcoming and before general results.
  • Each followed team shows its next fixture and latest result.
  • Optimistic follow/unfollow rolls back and explains failures.
  • Personal content remains outside the shared public cache.
Favourites and reminders
  • Match cards/detail expose favourite and scheduled reminder actions.
  • Signed-out actions preserve a callback to the originating match.
  • Settings lists saved matches and active reminders.
  • Copy remains honest: in-app reminders until push delivery exists.
Global search
  • Grouped player, team, and match results.
  • Two-character minimum, debounced requests, five results per group.
  • Keyboard navigation, highlighted matches, and bounded explicit-column queries.

Follow-on features

  • Shared stat glossary.
  • Canonical share actions and `.ics` calendar export.
  • Historical team/player season comparison.
  • PWA/push notifications only as a complete later permission and delivery project.

Phase 4 · Conditional architecture

Worker isolation & Rust gate

When to split the worker

  • Polling materially increases web-request p95.
  • Web CPU stays above 70% during representative live periods.
  • A poll routinely exceeds its scheduling interval.
  • Horizontal web scaling or duplicate-poller ownership becomes necessary.
  • Worker failures cause web restarts or missed updates.

TypeScript separation design

  1. Create a dedicated Render background worker from the existing modules.
  2. Use a PostgreSQL advisory lock for single ownership.
  3. Publish committed deltas through PostgreSQL LISTEN/NOTIFY first.
  4. Have the web process subscribe and forward through Socket.io.
  5. Recover canonical state from the database after missed notifications/reconnects.
  6. Remove in-process startWorker() only after cross-process broadcast is proven.
Rust gate. Require a CPU profile, representative benchmark, TypeScript baseline, isolated Rust prototype, at least a 3× throughput or material cost/latency improvement, and an ownership plan. Without those receipts, stay with TypeScript.

Proof before rollout

Testing & deployment

Required browser flows

  1. Home → filter team → load earlier results → open match.
  2. Match → Play by Play → filter → load older events.
  3. Standings → change season → open team.
  4. Live with no game → next fixture/reminder.
  5. Signed-out favourite → sign in callback → favourite saved.
  6. Settings → follow/unfollow → personalized home changes.
  7. Keyboard-only traversal through all primary controls.

Required viewports

1440 × 900, 1024 × 768, 390 × 844, and 320 × 568.

Deployment sequence

  1. Instrumentation and season-scoping tests.
  2. Bounded homepage and Live Hub.
  3. Cache wrappers.
  4. On-demand events and chart loading.
  5. Responsive/media/accessibility polish.
  6. Account discovery and personalization.
  7. Observe a live round before any worker split.

Every browser flow proves

  • Correct page identity and meaningful content.
  • No framework overlay or relevant console error.
  • The intended interaction and resulting state.
  • Desktop and mobile screenshot evidence.

Programme exit criteria

Definition of done

  • Phases 1–3 acceptance criteria pass.
  • The homepage no longer renders the full season initially.
  • Standings and team records are season-correct.
  • Live has a useful no-live state.
  • Play-by-play is on-demand and paginated.
  • Named accessibility risks are corrected and keyboard-tested.
  • Profile layouts and media fallbacks are visually verified.
  • Account and personalization are discoverable and functional.
  • Performance results are recorded against the audit baseline.
  • npm run check, npm run build, and Graphify refresh pass.
  • Rust remains explicitly evidence-gated.
  • Any deferred Phase 4 work has an explicit decision record.
The implementation principle

Query less. Render less. Cache stable data. Defer optional code and data. Measure what remains. Change runtime ownership—or language—only when the receipts justify it.
